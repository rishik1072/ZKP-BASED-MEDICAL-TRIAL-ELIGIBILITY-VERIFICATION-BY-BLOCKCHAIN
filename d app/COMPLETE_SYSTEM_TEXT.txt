- Poseidon Hashing (ZK-optimized)

SECTION 3: COMPLETE ENCRYPTION ARCHITECTURE
================================================================================

3.1 CREDENTIAL ENCRYPTION (AES-256-GCM)
=======================================

Medical credentials are encrypted using AES-256-GCM (Advanced Encryption Standard 
with Galois/Counter Mode). This is military-grade encryption.

CREDENTIAL JSON STRUCTURE:
{
  "patientId": "P123456789",              (unique patient identifier)
  "age": 35,                              (age in years, 0-150)
  "gender": "M",                          (M, F, or Other)
  "issuedAt": "2024-01-15T10:00:00Z",    (ISO 8601 timestamp)
  "issuerDID": "did:example:doctor123",  (doctor's DID)
  
  "medicalData": {                        (sensitive medical info)
    "hemoglobin": 14.5,                   (g/dL)
    "weight": 75,                         (kg)
    "bloodType": "O+",                    (blood type)
    "metalImplants": false,               (true/false)
    "pacemaker": false,                   (true/false)
    "pregnancy": false,                   (true/false)
    "lastCheckup": "2024-01-10"           (YYYY-MM-DD)
  },
  
  "encrypted": {                          (ENCRYPTION PAYLOAD)
    "method": "aes-256-gcm",              (encryption type)
    "iv": "base64_encoded_iv",            (initialization vector)
    "tag": "base64_encoded_tag",          (authentication tag)
    "ciphertext": "base64_encoded"        (encrypted data)
  },
  
  "rsaSignature": "base64_signature",     (doctor's digital signature)
  "nonce": 987654321                      (replay attack prevention)
}

HOW ENCRYPTION WORKS:
1. Doctor generates random 96-bit IV (Initialization Vector)
2. Medical data encrypted with AES-256 in GCM mode
3. GCM produces 128-bit authentication tag
4. Ciphertext is base64 encoded for JSON storage
5. Doctor signs credential with RSA private key
6. Nonce ensures proof cannot be replayed

ENCRYPTION PARAMETERS:
- Key Length: 256 bits (32 bytes)
- Algorithm: AES-256
- Mode: GCM (Galois/Counter Mode)
- IV Length: 96 bits (12 bytes)
- Auth Tag Length: 128 bits (16 bytes)
- Tag Verification: Prevents tampering detection

DECRYPTION PROCESS:
1. Extract IV, tag, and ciphertext from credential
2. Use AES-256 with GCM mode
3. Verify authentication tag (ensures data integrity)
4. Return plaintext medical data

3.2 RSA SIGNATURE VERIFICATION
==============================

Each credential carries RSA signature from the issuing doctor/institution.

RSA Key Details:
- Key Size: 4096 bits (high security)
- Format: PKCS#8 (Private), PKCS#1 (Public)
- Encoding: Base64 in environment variables

Signature Process:
1. Doctor creates credential JSON
2. Doctor signs with RSA private key
3. Signature is base64 encoded
4. Credential sent with signature

Verification Process:
1. Extract RSA public key from issuer DID
2. Verify signature against credential data
3. If valid: credential is authentic
4. If invalid: credential is rejected

Environment Keys:
RSA_PUBLIC_KEY=base64_encoded_public_key
RSA_PRIVATE_KEY=base64_encoded_private_key

3.3 POSEIDON HASHING
===================

Poseidon is a cryptographic hash function optimized for Zero-Knowledge Proofs.
Unlike SHA-256, Poseidon is very efficient inside Circom circuits.

Hash Function: Poseidon
Input: Credential data elements
Output: Fixed-size hash (credential commitment)

Hashed Elements:
- Patient ID
- Age
- Gender (1=M, 0=F)
- Issue timestamp
- Nonce

Hash Usage:
- Creates credential commitment (non-reversible)
- Used in ZKP public signals (revealed in proof)
- Enables proof linking to credential
- Cannot reverse hash to recover patient ID or medical data

Hash Property: One-Way
- Hash(credential) -> fixed hash value
- Cannot recover credential from hash
- Perfect for privacy protection

Environment Key:
ENCRYPTION_KEY=32_byte_hex_key_for_aes_256_gcm

5.1 WHAT IS A ZERO-KNOWLEDGE PROOF?
===================================

Definition:
A zero-knowledge proof is a cryptographic method where one party (prover) can 
convince another party (verifier) of the truth of a statement WITHOUT revealing 
any information about the statement itself.

In Medical Context:
Statement: "This patient is eligible for blood donation"
Proof: Cryptographic proof of statement
Revealed: ONLY: Yes/No (eligible or not)
Hidden: Age, hemoglobin level, weight, all medical data

Mathematical Properties:
- Completeness: Valid proof always verifies successfully
- Soundness: Invalid proof cannot verify successfully
- Zero-knowledge: Verifier learns nothing except the statement's truth

Proof System Used: Groth16
- Developed for zk-SNARK (zero-knowledge Succinct Non-interactive ARgument of Knowledge)
- Small proof size (~288 bytes)
- Fast verification (~1-2ms)
- Requires trusted setup once
- Industry standard

5.2 CIRCOM CIRCUIT: eligibility.circom
======================================

Location: circuits/src/eligibility.circom
Language: Circom 2.0
Purpose: Define eligibility rules as mathematical constraints

Circuit Inputs (Private - never revealed):
- age: Patient age in years
- testType: 0=Blood, 1=MRI, 2=CT
- hemoglobin: Hemoglobin level * 100 (to avoid decimals)
- weight: Weight in kg
- metalImplants: 1=has, 0=no
- pacemaker: 1=has, 0=no
- pregnancy: 1=yes, 0=no
- nonce: Random number (replay protection)

Circuit Outputs (Public - revealed):
- eligible: 1=eligible, 0=not eligible
- credentialHash: Poseidon hash of credential

BLOOD DONATION TEST RULES
-------------------------
Eligibility Conditions (ALL must be true):
1. Age > 18 years
2. Hemoglobin >= 12.5 g/dL (female) or >= 13.5 g/dL (male)
3. Weight > 50 kg

Circuit Logic:
bloodEligible = (age > 18) AND (hemoglobin > 1250) AND (weight > 50)

MRI SCAN TEST RULES
-------------------
Eligibility Conditions (ALL must be true):
1. Age > 5 years
2. NO metal implants (metalImplants = 0)
3. NO pacemaker (pacemaker = 0)
4. NOT pregnant (pregnancy = 0)

Circuit Logic:
mriEligible = (age > 5) AND (metalImplants == 0) AND 
              (pacemaker == 0) AND (pregnancy == 0)

Contraindications (make ineligible):
- Active pacemaker
- Recent metallic implants that cannot be removed
- Current pregnancy

CT SCAN TEST RULES
------------------
Eligibility Conditions (ALL must be true):
1. Age >= 18 years
2. Weight < 160 kg
3. NOT pregnant (pregnancy = 0)

Circuit Logic:
ctEligible = (age >= 18) AND (weight < 160000) AND (pregnancy == 0)

Contraindications:
- Current pregnancy
- Metallic implants (contrast-containing)
- Recent barium studies (can interfere)

CIRCUIT SELECTION LOGIC
-----------------------
Based on testType input (0, 1, or 2):
- If testType == 0: Use bloodEligible
- If testType == 1: Use mriEligible
- If testType == 2: Use ctEligible

Final Output:
eligible = selected_eligibility_result

Constraint System:
- Circom compiles to polynomial constraints
- Each constraint becomes arithmetic equation
- Prover must satisfy ALL constraints
- Verifier checks constraints prove statement

5.3 PROOF GENERATION PROCESS
============================

Step 1: Prepare Inputs
- Extract medical data from credential
- Convert to circuit format (integers, integers, integers)
- Include nonce for replay protection
- Create CircuitInputs object

Step 2: Generate Witness
- Input: CircuitInputs + eligibility.wasm (WASM file)
- WASM File: circuits/dist/eligibility_js/eligibility.wasm
- Process: Execute circuit with inputs
- Output: Witness data (satisfies all constraints)
- Time: ~100-500ms

Step 3: Generate Proof
- Input: Witness + eligibility_0001.zkey (proving key)
- Proving Key: circuits/dist/eligibility_0001.zkey
- Process: Groth16 algorithm generates cryptographic proof
- Output: proof + publicSignals
- Time: ~500ms-2s depending on circuit size

Step 4: Parse Proof Components
- pi_a: First component of proof (2 numbers)
- pi_b: Second component of proof (2x2 matrix)
- pi_c: Third component of proof (2 numbers)
- publicSignals[0]: Eligibility (1 or 0)
- publicSignals[1]: Credential hash (non-reversible)

Example Proof Output:
{
  "proof": {
    "pi_a": [
      "12345678901234567890123456789012345678901234567890",
      "98765432109876543210987654321098765432109876543210"
    ],
    "pi_b": [
      [
        "11111111111111111111111111111111111111111111111111",
        "22222222222222222222222222222222222222222222222222"
      ],
      [
        "33333333333333333333333333333333333333333333333333",
        "44444444444444444444444444444444444444444444444444"
      ]
    ],
    "pi_c": [
      "55555555555555555555555555555555555555555555555555",
      "66666666666666666666666666666666666666666666666666"
    ]
  },
  "publicSignals": [
    "1",                    (1 = eligible, 0 = not eligible)
    "0x9c22ff5f21f0b81b" (credential hash)
  ],
  "credentialHash": "0x9c22ff5f21f0b81b",
  "eligible": true
}

5.4 PROOF VERIFICATION PROCESS
==============================

Local Verification (Backend):
1. Input: proof + publicSignals + verification_key.json
2. Verification Key: circuits/dist/verification_key.json
3. Process: snarkjs.groth16.verify()
4. Check: Does proof satisfy all constraints?
5. Output: true/false
6. Time: ~1-2ms

On-Chain Verification (Blockchain):
1. Input: proof (pi_a, pi_b, pi_c) + publicSignals
2. Process: Groth16Verifier contract
3. Check: Verify proof on Polygon
4. Output: boolean success
5. Gas Cost: 1-2M gas
6. Time: ~15 seconds (block confirmation)

Verification Guarantees:
- If verification passes: Proof is mathematically valid
- If verification fails: Proof is invalid or data was tampered with
- Cannot forge a proof without solving hard math problem
- Soundness error: negligible (1 in 2^254)

No Information Leaked:
- Verifier only learns: Yes/No (eligible)
- Cannot determine age from proof
- Cannot determine medical values from proof
- Cannot reverse engineer patient ID from proof
- Cannot forge proof for different eligibility status
- Cannot reuse proof twice (nonce prevents this)

5.5 PROOF SECURITY PROPERTIES
=============================

Completeness:
- Valid proof will ALWAYS verify successfully
- Cannot reject legitimate eligibility proofs

Soundness:
- Invalid proof will NEVER verify successfully
- Cannot accept forged or tampered proofs
- Soundness error: < 1 in 10^76

Zero-Knowledge:
- Verifier learns NOTHING except eligibility status
- Cannot extract medical data from proof
- Cannot determine which medical field failed eligibility
- Cannot link different proofs to same patient (with nonce)

Succinctness:
- Proof size: ~288 bytes (very small)
- Verification time: ~1-2ms (very fast)
- Independent of circuit complexity

Non-Interactivity:
- Prover creates proof once
- Verifier can check it anytime
- No back-and-forth communication
- Can be stored on blockchain permanently

Replay Protection:
- Nonce prevents same proof reuse
- Each proof has unique nonce
- Cannot submit same proof twice for eligibility
- Timestamp on blockchain prevents replay from old proofs

Backend Processing (proofService.ts):
1. Receive proof + publicSignals
2. Load verification key: verification_key.json
3. Call snarkjs.groth16.verify():
   - Check proof satisfies all constraints
   - Verify proof matches publicSignals
4. Return {valid: true/false}

Time: 1-2 milliseconds
Frontend: Show verification status (success or failure)


Stage 3c: Store Proof On-Chain
API Endpoint: POST /api/zk/store-on-chain

Backend Processing (contractService.ts):
1. Prepare proof for smart contract:
   - Convert pi_a, pi_b, pi_c to contract format
   - Convert credentialHash to bytes32
   - Extract eligible status

2. Check if user provided private key:
   - If yes: Use user's key for signing
   - If no: Use backend's PRIVATE_KEY_BLOCKCHAIN

3. Create signer:
   const signer = new ethers.Wallet(privateKey, provider)

4. Create contract instance:
   const contract = new ethers.Contract(
     contractAddress,
     VERIFIER_ABI,
     signer
   )

5. Call contract function:
   const tx = await contract.storeResult(
     credentialHashBytes32,
     eligible
   )

6. Wait for transaction confirmation:
   const receipt = await tx.wait()

7. Return transaction details:
   - transactionHash
   - blockNumber
   - gasUsed
   - timestamp

Time: 15-60 seconds (blockchain confirmation)
Cost: 1-2M gas (~$0.01-0.03 at typical rates)

On-Chain Storage:
- Credential hash stored in mapping
- Eligibility status (1 bit) stored
- Timestamp recorded
- Verifier address recorded
- Event emitted for transparency

SECTION 12: TROUBLESHOOTING
================================================================================

Common Issues & Solutions:

ISSUE: "Missing required field: credential"
CAUSE: No credential object in request
SOLUTION: Include full credential JSON in POST request body

ISSUE: "Invalid age: must be a number between 0 and 150"
CAUSE: Age field invalid (wrong type or out of range)
SOLUTION: Verify age is number and 0 <= age <= 150

ISSUE: "Unsupported encryption method. Expected: aes-256-gcm"
CAUSE: Different encryption method used
SOLUTION: Change credential.encrypted.method to "aes-256-gcm"

ISSUE: "Blockchain service not initialized"
CAUSE: PRIVATE_KEY_BLOCKCHAIN or CONTRACT_ADDRESS missing
SOLUTION: Add missing environment variables to .env

ISSUE: "Insufficient funds for gas"
CAUSE: Wallet doesn't have enough MATIC
SOLUTION: Fund wallet (add MATIC tokens)

ISSUE: "Proof verification failed"
CAUSE: Proof is forged or tampered with
SOLUTION: Generate new proof with correct credential

ISSUE: "WASM file not found: eligibility.wasm"
CAUSE: Circuit files not compiled
SOLUTION: Run: npm run setup:circuits

ISSUE: "Connection refused: Cannot connect to RPC"
CAUSE: Wrong RPC URL or network down
SOLUTION: Check POLYGON_RPC_URL is correct

ISSUE: "Certificate verification failed" (CORS error)
CAUSE: Frontend domain not in ALLOWED_ORIGINS
SOLUTION: Add frontend URL to ALLOWED_ORIGINS in .env

ISSUE: "Nonce must be a positive number"
CAUSE: Nonce field invalid or missing
SOLUTION: Provide positive number for nonce (> 0)

ISSUE: "Proof timestamp already used" (replay attack)
CAUSE: Same proof submitted twice
SOLUTION: Generate new proof with different nonce

ISSUE: "Cannot read property 'eligible' of undefined"
CAUSE: Response from backend is malformed
SOLUTION: Check backend logs for errors

ISSUE: "Transaction rejected - invalid signature"
CAUSE: Wrong private key used for signing
SOLUTION: Verify private key is correct and funded

ISSUE: "Block not yet mined" (after transaction)
CAUSE: Transaction still pending
SOLUTION: Wait 15-60 seconds for confirmation
